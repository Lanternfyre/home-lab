# A node will not rejoin after a reboot

For the cluster operator: start here when a rebooted node is absent, `NotReady`, or remains cordoned. The initial checks are read-only; they do not establish that storage works or authorize an uncordon. The commands below are **untested in this draft**. The linked recovery procedures record earlier incidents or tests, but have not been run for this incident.

## Identify the node and its role

1. **Untested here; read-only.** From a workstation with cluster access, run `kubectl get nodes -o wide`. Record the Kubernetes name (`k8s-labN` or `k8s-edge1`), Ready state, and whether scheduling is disabled. A missing node may not appear at all. Inventory names (`k8s-N`, `edge-1.edge`) differ; use [the inventory groups](../../ansible/README.md#roles-and-groups) to determine whether the host is a server or agent. If the API is unreachable, check a known server locally before concluding that this node alone failed.
2. **Untested here; read-only.** On the affected host, run `systemctl is-active k3s.service` for a server or `systemctl is-active k3s-agent.service` for an agent. Check recent errors locally with `sudo journalctl -u k3s.service -b --no-pager -n 100` or the corresponding `k3s-agent.service` command. **Redact any credential before sharing logs.** Agents have no local kubeconfig or etcd; use `kubectl` from the workstation or `k3s kubectl` on a server. See [Ansible roles and groups](../../ansible/README.md#roles-and-groups).

## If a server is not starting

1. **Untested here; read-only.** Check whether another server and the API are healthy before considering any recovery. If the journal says `cred/passwd newer than datastore`, follow the diagnosis in [Cluster join token: what 2026-09-07 taught us](../../CLUSTER-TOKEN.md#what-2026-09-07-taught-us). If it says `bootstrap data already found and encrypted with different token`, use [the separate 2026-09-06 incident analysis](../../CLUSTER-TOKEN.md#what-2026-09-06-taught-us). These messages indicate different token/datastore states; neither calls for deleting a file as a routine first step.
2. **Untested here; read-only.** If the node is waiting for the API VIP during a cold start, check whether a healthy server holds the VIP. [Modernization's VIP finding](../../MODERNIZATION.md) records that already joined nodes use direct peer connections, while a cold start can wait for a VIP holder. Do not repoint `--server` just to bypass that wait. On the public edge agent, the bootstrap target is instead k8s-1's fixed LAN address over WireGuard; see [its inventory setting](../../ansible/inventory/group_vars/k3s_edge.yml).
3. **Operator review required before action; destructive or credential-changing; untested here.** The [token runbook](../../CLUSTER-TOKEN.md) contains a supported datastore re-save and, separately, recovery involving token rotation, server-data deletion, and etcd member removal. Confirm the diagnosis, quorum, snapshot, and archived token with the operator before using any of those procedures. Its `curl -u server:<candidate>` and inline `--token` examples are historical: never run them with real tokens substituted on a command line. Choose a secret-safe recovery method before executing any token-dependent step. Do not put a token in a log, issue, or this page. An existing etcd datastore also causes k3s to ignore `--cluster-init` and `--server`; an empty-disk rebuild can create an unintended new cluster ([Modernization's datastore finding](../../MODERNIZATION.md)).

## If an agent is not starting

1. **Untested here; read-only.** Use the `k3s-agent.service` result and journal from above. Check whether its configured bootstrap target is reachable from that host, and whether a healthy server and API exist. A home agent normally targets the VIP; `k8s-edge1` targets k8s-1 over WireGuard ([config template](../../ansible/roles/k3s_config/templates/config.yaml.j2), [edge inventory](../../ansible/inventory/group_vars/k3s_edge.yml)). Do not copy a server's config onto an agent: server-only keys make the agent refuse to start.
2. **Untested here; read-only.** If failure began after an installer or upgrade, inspect only the *presence* of `server:` and `token-file:` keys in `/etc/rancher/k3s/config.yaml` with `sudo awk -F: '/^(server|token-file):/ {print $1 ": [configured]"}' /etc/rancher/k3s/config.yaml`. Do not print token files or `K3S_TOKEN` from a service environment. [The token runbook](../../CLUSTER-TOKEN.md) explains that an old agent `K3S_TOKEN` environment value overrides `token-file`, while the installer used by [30-upgrade.yml](../../ansible/playbooks/30-upgrade.yml) regenerates the service environment. Have the operator compare the live configuration with the Ansible source before changing it.

## Before returning any node to service

1. **Untested here; read-only.** Check the node's Ready and cordon state with `kubectl get node <kubernetes-node-name>`. For a storage-enabled home node, `kubectl get csinode <kubernetes-node-name> -o jsonpath='{.spec.drivers[*].name}'` shows driver registration, **not** a working volume. `Ready` and a nonempty CSINode do not satisfy the [storage invariant](standing-warnings.md#nodes-and-storage).
2. **Untested here; mutating; operator review before use.** If a recovered home node remains cordoned, use the [standalone storage proof](../../ansible/playbooks/46-prove-node-storage.yml) only after checking its preconditions. It provisions, mounts, and writes to a test volume; cleanup is attempted, but pod or PVC deletion can fail and a PV can remain. Check for leftover resources. The playbook can uncordon on a successful proof. Supply the Kubernetes node name. The edge node has no CSI by design and uses the [WireGuard/CNI proof](../../ansible/playbooks/tasks/prove-and-uncordon-edge.yml) instead.

**Upgrade caveat, verified from repository code; not tested live here:** [30-upgrade.yml](../../ansible/playbooks/30-upgrade.yml) checks CSINode registration before its normal uncordon, then runs the real storage proof in a later play. Its interrupted-hop shortcut can also uncordon an already-upgraded node without that proof. Thus the upgrade playbook does **not** enforce a successful mounted-volume proof before every uncordon. Review this ordering with the operator before relying on an upgrade run to return a node safely to service.
